**Status:** Draft v0.1 — **pre-freeze**: the wire format may still change.
This document is *the* protocol contract; it supersedes the earlier numbered
drafts (`00-overview.md` … `05-security-goals.md`), which have been retired and
remain available in git history.

**Name:** IMP — IMP Message Protocol.

**Canonical copy:** <https://github.com/despulii-bit/imp>, at
`protocol/spec/v0.1.md`, tagged `v0.1.0`. Cite the tag, not a branch: a tag is

**License:** CC0 1.0 Universal (see `LICENSE`). The contract belongs to

**Formalization:** Lean 4, `protocol/formal/` (namespace `Imp`). Every

**Conformance:** Annex B ([`conformance.md`](conformance.md)) with
machine-readable vectors in [`vectors/v0.1.json`](vectors/v0.1.json).

## Conventions

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT,
RECOMMENDED, MAY, and OPTIONAL are to be interpreted as described in
[RFC 2119].

- **Normative requirements** are numbered `REQ-x.y` and are binding.
- **Security goals** are numbered `SEC-n` and are the claims the formalization
  targets.
- Text marked *(non-normative)* is explanation and rationale; implementers may
  ignore it.
- **Proof references** look like `Imp.validate_ok_implies_sig` and
  resolve to declarations in `protocol/formal/`.
- *(impl obligation)* marks a requirement whose mechanical verification is
  deferred, with the obligation stated.

**Scope of this project.** This document and the Lean proofs are the entire
deliverable. Senders, receivers, clients, bridges, and relays are separate
programs built against this contract by anyone; the protocol project produces
no software and blesses no implementation (REQ-8.4).

# 1. Introduction

## 1.1 The problem (non-normative)

Email is hard to self-host because deliverability depends on **reputation**:
new domains and IPs must warm up for weeks, sending requires privileged port 25
(blocked by most residential ISPs and by AWS/Azure/GCP), and receivers answer
to a handful of gatekeepers. The recommended "fix" is to route through a
third-party relay service — the very dependency this protocol exists to remove.

## 1.2 What IMP does (non-normative)

IMP replaces reputation with a **cryptographic check performed at message
time**:

- A **domain publishes its keys** in DNS. A message from `user@example.com`
  either verifies against a key that `example.com` itself published for that
  instant, or it is rejected. There is no warm-up, no history, no score.
- **Delivery is an HTTPS POST** to a discovered endpoint, on port 443, using
  the same TLS infrastructure as any website.
- **Every message is signed.** Accepted messages are attributable to a key
  that the sender's own domain vouches for.
- **The receiving decision remains local.** The protocol authenticates;
  whether to accept a given sender is receiver policy.

The identity is the **key set**. The domain is how that key set is *published
and addressed* — and the domain need not be owned by the identity holder
(§2.6, delegation).

## 1.3 How it works: the life of a message (non-normative)

**Setup (once).** Generate an Ed25519 keypair. Publish one DNS record at
`_imp-key.<domain>` saying "this domain's identity at address `local@<domain>`
is this public key, valid between `nb` and `na`". Ensure an endpoint exists at
`https://<domain>/.imp/v1/deliver`. That is the entire setup: no PTR record,
no SPF/DKIM/DMARC, no IP warm-up, no port 25.

**Sending.** To send to `alice@example.net`:

1. Discover the endpoint (SRV record, or the default path).
2. Build the **envelope**: `from`, `to`, a random `msgid`, `ts`, `type`,
   `payload`, and the `kid` of the signing key.
3. **Sign** the canonical serialization with *your own domain's* key. The
   sender signs; the receiver verifies against the sender's published key.
4. **POST** over HTTPS. On `202`, done. Otherwise retry the *identical bytes
   with the same `msgid`*.

**Receiving.** The receiver runs the gate of §6 in order: version → resolve
the sender's key and epoch → verify the signature → check freshness → check
that the `msgid` is new → accept durably and reply `202`.

```
Sender (ci.sender.example)                          Receiver (example.net)
 1. where does example.net receive? ──► DNS SRV / well-known
 2. envelope {v,from,to,msgid,ts,type,payload,kid}
 3. sign with SENDER'S key (canonical bytes)
 4. HTTPS POST ──────────────────────────────────────► 5. gate:
                                                         version? key? epoch?
                                                         signature? fresh? new?
                                                        (store, mark, 202)
 ◄────────────────────────────────────────────────────── 6. 202 / 4xx / 505
 7. no answer? retry the SAME msgid later ─────────────► duplicate → 409
```

**Rotation (non-normative).** Keys have finite epochs. Before a key expires,
the domain publishes its successor, *cross-signed by the current key*, with an
overlapping epoch, so in-flight mail verifies under either key. A key id is
never reused. To revoke, remove the record; short TTLs make the removal
propagate within minutes and fail closed.

## 1.4 Roles (non-normative)

| Role | Responsibility |
|---|---|
| **Identity holder** | Holds the private key; signs messages it sends |
| **Namespace owner** | Publishes the key records for a domain (may be the identity holder, or a delegate) |
| **Sender** | Any program that builds, signs, and delivers envelopes |
| **Receiver** | The HTTPS endpoint that performs the gate and accepts messages |
| **DNS** | The discovery/publication fabric (no DNSSEC requirement) |

## 1.5 Principles (normative)

- **REQ-1.1** Authentication MUST be a cryptographic check against key data the
  sender's own domain publishes. No age, volume, history, IP, or third-party
  score may be required for a message to be authenticated.
- **REQ-1.2** Delivery MUST use HTTPS on port 443. No protocol function may
  depend on port 25 or on privileged sending infrastructure.
- **REQ-1.3** Receivers MUST verify every incoming message's signature and
  MUST NOT accept a message that fails verification.
- **REQ-1.4** Acceptance policy (whom to accept from) is receiver-local. The
  protocol MUST NOT define reputation scoring; receivers SHOULD default to
  denying unknown senders.
- **REQ-1.5** Receivers MUST NOT relay or forward messages to third parties.
- **REQ-1.6** Security-relevant requirements MUST be backed by a Lean theorem
  or an explicitly tracked open obligation (§9).

## 1.6 Non-goals (normative)

- **REQ-1.7** v0.1 defines no confidentiality: no end-to-end encryption.
  Payload confidentiality is limited to TLS in transit.
- **REQ-1.8** v0.1 defines no message types beyond `notification`, `event`,
  and `app`, and no command/reply semantics (`in_reply_to` is reserved only).
- **REQ-1.9** v0.1 defines no email interoperability, no bridges, no relay
  role, no group/multicast messaging, and no payments or proof-of-work.

## 1.7 Spam and abuse model (non-normative)

Email defends against spam with **price and guessing**: reputation scores, IP
warm-up, relay services, and content filters. It must, because it cannot
reliably tell who the sender is — a `From:` header is forgeable, so the only
remaining levers are economics and pattern-matching. IMP has a *permission*
primitive (a verifiable identity), so it can defend differently: decide **who
may speak**, instead of scoring how suspicious a message looks.

### What IMP prevents inherently

These fall out of authentication and need no policy:

| Abuse | Why it cannot happen | Requirement |
|---|---|---|
| Spoofing / impersonation | A `from` domain must verify against that domain's own published key | REQ-1.1, REQ-6.1.4 |
| Open relaying / amplification | Receivers must not forward to third parties | REQ-1.5, REQ-5.8 |
| Backscatter | Delivery is a synchronous request with a response; there is no separate bounce channel | §5.3 |
| Untraceable / unblockable senders | Every accepted message is bound to a domain key; blocking is per key or per domain | REQ-5.9 |
| Coarse rate limiting | One authenticated identity per message allows precise per-key limits | REQ-5.8 |

### What IMP cannot prevent

- A **first message from a new key to an open inbox**. The message is valid;
  only receiver policy can refuse it.
- **Cheap identity rotation.** A spam operator can register domains at the
  price of a domain registration. Cost is a speed bump, not a wall.
- **A compromised key or domain.** Spam from a hijacked identity is
  indistinguishable from that identity's real mail until it is revoked (§3.3).
- **Delegated-label abuse.** Because a namespace owner publishes `sub=`
  records (REQ-2.9), a provider that mints addresses cheaply can be abused to
  mint spam identities — but the *domain* then absorbs the blocking fallout,
  which pressures namespace owners to police their tenants. That is
  accountability email lost when shared IPs diluted it.
- **Cold contact without spam.** These cannot both hold without a price
  mechanism; that is a property of the problem, not of this design.

### Receiving policy: the three archetypes

| Policy | Spam | Cold contact | Cost |
|---|---|---|---|
| **Closed by default** (vouching / allow-list) | Structurally impossible | Must be invited | Consent flow |
| **Open + authenticated** | Arrives, but is attributable and blockable | Preserved | Receiver-side blocking |
| **Open + metered** (proof-of-work / fee) | Priced | Preserved | Taxes legitimate senders; rejected in v0.1 (REQ-1.9) |

The recommended default is deny-unknown (REQ-1.4).

### Why closed-by-default is not specified here

Closed-by-default, allow-lists, block-lists, rate limits, invitations, and
quarantine are **local policy**: they are one side's decisions, not a wire
agreement, and each can be implemented one layer above the protocol. By the
project's scope rule they are therefore deliberately *not* specified by IMP. A
future companion document ("IMP application conventions", explicitly
non-protocol) may standardize invitation or block-list *formats* where
ecosystem interop is useful — without touching the core contract.

What the protocol itself contributes to spam control is only this:
authentication (which makes permission possible and kills spoofing), a
machine-readable refusal vocabulary (REQ-5.5, REQ-5.11), the no-relay rule,
and a transparency requirement (REQ-5.10) so users can tell an open inbox from
a closed one.

# 2. Identity, Keys, and Addressing

## 2.1 Addresses

- **REQ-2.1** An address is `local@domain`, where `local` is a UTF-8 label and
  `domain` is an IDNA-valid DNS name.
- **REQ-2.2** The address's identity is the **key set** published for it. The
  domain is the publication and discovery point, not the identity itself.

## 2.2 Key records

- **REQ-2.3** Key records are published as TXT records at
  `_imp-key.<domain>` in the following format (fields `;`-separated, no
  whitespace):

  ```
  v=imp1;alg=ed25519;k=<b64>;kid=<b64>;nb=<unix>;na=<unix>[;sub=<label>][;sigprev=<b64>]
  ```

  | Field | Meaning |
  |---|---|
  | `v` | record version; MUST be `imp1` in v0.1 |
  | `alg` | signature algorithm; MUST be `ed25519` in v0.1 |
  | `k` | base64 (standard, padded) of the 32-byte raw Ed25519 public key |
  | `kid` | key id: base64 of the first 16 bytes of SHA-256 over the raw public key |
  | `nb` | epoch start, Unix seconds, inclusive |
  | `na` | epoch end, Unix seconds, inclusive |
  | `sub` | address label this key serves; absent means the label `*` (see REQ-2.6) |
  | `sigprev` | base64 Ed25519 cross-signature by the predecessor key (§3.2); REQUIRED on every non-genesis record |

  A record value longer than 255 bytes (possible with a long `sub`) MUST be
  published as multiple consecutive DNS character-strings whose in-order
  concatenation is the record value; no separator is inserted between them.
  This is the standard DNS multi-string convention and does not change the
  value's meaning.

- **REQ-2.4** The `kid` MUST be derived exactly as specified in REQ-2.3, so
  that all implementations compute the same key id.
- **REQ-2.5** The DNS TTL of key records MUST be ≤ 300 seconds.
- **REQ-2.6** A key record MAY carry `sub=<label>` to serve the address
  `<label>@<domain>`; a record without `sub` serves all labels (`sub=*`).
  For an address `local@domain`, resolution prefers a record with
  `sub=local`; if none exists, records without `sub` apply.
- **REQ-2.7** Every key record MUST have a finite epoch: `nb` ≤ `na`, both
  finite.
- **REQ-2.8** A `kid` MUST NOT be reused by a domain, ever, even after
  expiry.

## 2.3 Delegation (defined; not implemented in v0.1)

- **REQ-2.9** Publishing a `sub=<label>` record for a label the namespace
  owner does not itself operate is **delegation**: the private key remains
  with the identity holder; the domain vouches for the address.
  *(non-normative)* This is how an identity without its own domain obtains a
  globally resolvable address. The namespace owner retains the inherent powers
  of publication: it can revoke (delete the record) and can substitute a
  different key for the label. Use a self-owned domain for full independence;
  use delegation for convenience. This trade-off MUST be documented for users
  by implementations.

## 2.4 Resolution

- **REQ-2.10** To authenticate a message whose `from` is `local@domain`, `kid`
  is `kid`, and timestamp is `ts`, a receiver MUST:

  1. Fetch the `_imp-key.<domain>` TXT records.
  2. Select records serving `local` per REQ-2.6 whose `kid` equals the
     message's `kid`.
  3. Among those, require one whose epoch satisfies `nb ≤ ts ≤ na`.
  4. Verify the message signature under that record's `k`.
  5. Reject if no record matches (403), if only records with non-covering
     epochs match (410), or if the signature fails (401).

  Records at `_imp-key.<domain>` that do not match the REQ-2.3 format MUST be
  ignored; they neither match nor fail the lookup. If no valid record matches
  the `kid`, the outcome is `403` (`key_unknown`).

- **REQ-2.11** Receivers MUST bound the lifetime of cached key records by the
  record TTL (REQ-2.5). *(impl obligation: bounded cache; fail closed on
  expiry.)*

## 2.5 DNS properties

- **REQ-2.12** DNSSEC is RECOMMENDED but MUST NOT be required for
  interoperability. The threat model assumes an attacker may read, forge, or
  delete ordinary DNS records. Cross-signing (§3) prevents key *introduction*
  but not record *deletion*; deletion is a denial of service and fails closed.

# 3. Key Rotation and Revocation

## 3.1 Genesis

- **REQ-3.1** The first key of an address (the **genesis key**) is
  bootstrapped out of band: a receiver that has never held a key for a domain
  accepts the first valid record set subject to receiver policy (for example,
  explicit allow-listing or manual approval on first contact). Receivers MUST
  NOT accept a *rotation* from a key they have not previously held as
  authoritative.

## 3.2 Rotation and cross-signing

- **REQ-3.2** To rotate, the namespace owner publishes a new record whose
  `sigprev` is an Ed25519 signature by the **current key** `K` over the
  canonical key-record bytes of the successor `K'`. Those bytes are the
  record's fields in the order `v=…;alg=…;k=…;kid=…;nb=…;na=…`, with
  `;sub=…` appended if the record carries `sub`, and with `sigprev` omitted;
  they are UTF-8 encoded. (Pinned by the rotation vectors R1–R5.)
- **REQ-3.3** A receiver MUST treat a record as authoritative only if either

  1. it is the genesis record per REQ-3.1, or
  2. its `sigprev` verifies under a key currently held as authoritative for
     the same address, and

  in case 2, additionally:

  3. `K'.kid ≠ K.kid` (REQ-2.8), and
  4. the epochs overlap: `K'.nb ≤ K.na` (REQ-3.4).

  The result MUST be retained as an ordered **key chain**; its head is the
  current key. `[SEC-4]`

- **REQ-3.4** Rotations MUST overlap epochs (`nb(K') ≤ na(K)`), so a message
  timestamped during the transition verifies under at least one published key.
  `[SEC-5]`
- **REQ-3.5** Keys MUST NOT be reintroduced: a `kid` that has appeared once in
  a domain's chain MUST NOT appear again. `[SEC-4]`

## 3.3 Revocation

- **REQ-3.6** To revoke a key, the namespace owner removes its record and
  rotates to a fresh key. Because TTL ≤ 300 s (REQ-2.5), removal propagates
  within minutes. Receivers MUST fail closed once a record is no longer
  present in a refreshed cache.
- **REQ-3.7** A receiver MAY additionally treat the absence of a previously
  held record as a revocation signal. *(non-normative)* Key compromise is
  therefore bounded by the cache lifetime plus the owner's revocation speed.

# 4. The Envelope

## 4.1 Representation

- **REQ-4.1** A message is a JSON object with media type `application/imp+json`,
  UTF-8 encoded.

## 4.2 Members

- **REQ-4.2** The envelope members are:

  | Member | Type | Meaning |
  |---|---|---|
  | `v` | integer | wire version; MUST be `1` in v0.1 |
  | `from` | string | sender address (`local@domain`) |
  | `to` | array of string | recipients; MUST contain exactly one address in v0.1 (unicast) |
  | `msgid` | string | idempotency/replay key, base64 of 16 random bytes |
  | `ts` | integer | send time, Unix seconds |
  | `type` | string | message type (§4.4) |
  | `payload` | string | base64 of opaque payload bytes |
  | `kid` | string | key id of the signing key (REQ-2.3) |
  | `sig` | string | base64 Ed25519 signature over REQ-4.9 |
  | `in_reply_to` | string | **RESERVED**; senders MUST NOT set it in v0.1 |

- **REQ-4.3** `msgid` MUST be generated from at least 128 bits of randomness
  and MUST NOT be reused by the same sender domain for different payloads. It
  is the idempotency key (§5.6) and the replay key (§6).
- **REQ-4.4** `ts` MUST be the sender's current time in Unix seconds and MUST
  fall within the receiver's freshness window (§6, REQ-6.1.5).
- **REQ-4.5** `payload` MUST decode to at most 1 MiB in v0.1.
- **REQ-4.6** `in_reply_to` is reserved for a future version. Receivers
  MUST ignore it; it MUST NOT affect verification.

## 4.3 Canonical serialization and signature

- **REQ-4.7** The **canonical serialization** of an envelope is UTF-8 JSON
  with:

  1. object members sorted by name in byte-wise lexicographic order of the
     UTF-8 encoding of the name;
  2. no insignificant whitespace;
  3. strings UTF-8 encoded with only the escapes JSON requires;
  4. integers in minimal decimal (no leading zeros, no `+`, no exponent);
     fractional numbers are not permitted in v0.1;
  5. arrays preserving element order (`to` is a single-element array in v0.1);
  6. binary-valued members (`k`, `kid`, `payload`, `sig` where applicable)
     using standard base64 with padding.

  Canonical serialization MUST be applied to the *complete member set present*
  in the envelope, including members not defined by v0.1 (REQ-7.3).

- **REQ-4.8** The **signature input** is the canonical serialization of the
  envelope with the `sig` member omitted. `sig` is a base64 Ed25519 signature
  (64 bytes) over exactly those bytes, produced with the sender's private key.
  Because `v` and all other members are covered, no member — including the
  version — can be altered without invalidating the signature. `[SEC-1]`
- **REQ-4.9** The canonical serialization MUST be injective: distinct envelopes
  MUST yield distinct bytes. `[SEC-2]`

  *(formal status)* The **framing** is proved: `Imp.encBlocks_injective`
  shows the self-delimiting block encoding is unambiguous, and
  `Imp.body_injective` / `Imp.signatureInput_injective` (module
  `Imp.Canonical`) show that the canonical sequence of member blocks
  determines the members exactly — covering ordering, block boundaries, and
  the fixed quoted member names. The **decimal-integer** and **JSON-string**
  encoders are proved injective (`Imp.encNat_injective`,
  `Imp.encStr_injective`; module `Imp.Text`). Base64 is proved in full: the bit
  packing (`Imp.byte0_sextet0` …), the RFC 4648 alphabet
  (`Imp.b64val_b64char`, `Imp.b64char_ne_pad`), the padded assembly
  (`Imp.decB64_encB64`), and injectivity (`Imp.encB64_injective`) — all in
  module `Imp.Base64`. The v0.1 `to` framing is proved in `Imp.Text`
  (`Imp.encArray1_injective`). **Obligation #8b is closed.**
- **REQ-4.10** The signature scheme is abstractly correct: a signature
  produced with a private key verifies under the corresponding public key
  (`Imp.SignatureScheme.sign_verify`). Concrete Ed25519 soundness is
  a trusted assumption (§9).

## 4.4 Message types

- **REQ-4.11** `type` identifies the payload's intended interpretation. v0.1
  defines `notification` (human-readable notice), `event` (machine-actionable
  structured event), and `app` (application-defined). The registry mechanism
  for new types is additive (REQ-7.4).
- **REQ-4.12** Verification MUST NOT depend on `type`. A receiver MUST NOT
  fail verification solely because `type` is unknown; payload interpretation
  is application policy.
- **REQ-4.13** The base64-valued members MUST decode to exactly the stated
  lengths: `kid` 16 bytes, `msgid` 16 bytes, `sig` 64 bytes; `payload` MUST be
  valid base64 (any length up to the limit of REQ-4.5). A receiver MUST reject
  a member that is not valid base64 or decodes to the wrong length with `400`
  (`malformed`). This check belongs to well-formedness (step 2 of REQ-6.1) and
  precedes key resolution.

# 5. Delivery

## 5.1 Endpoint discovery

- **REQ-5.1** A domain MAY publish `_imp._tcp.<domain>` SRV records selecting
  the delivery endpoint host and port. If absent, the endpoint defaults to
  `https://<domain>/.imp/v1/deliver`.
- **REQ-5.2** The endpoint host MUST present a TLS certificate valid for that
  host, chaining to a publicly trusted CA. Plaintext HTTP MUST NOT be used.
  *(non-normative)* DANE-style certificate pinning is future work.

## 5.2 Submission

- **REQ-5.3** A sender submits a message with
  `POST https://<endpoint>/.imp/v1/deliver`, `Content-Type:
  application/imp+json`, body = the envelope's canonical serialization
  (REQ-4.7), unmodified.
- **REQ-5.4** The sender MUST sign with a key that its own domain currently
  publishes for its own `from` address, with an epoch covering `ts`.

## 5.3 Responses

- **REQ-5.5** Responses MUST use the following status codes. A response body,
  when present, MUST have media type `application/json` and SHOULD be
  `{"error": "<token>"}` with the listed token. The body is informative: it
  carries no protocol state and MUST NOT be required for interoperability.

  | Status | Token | Meaning | Sender action |
  |---|---|---|---|
  | `202` | — | Accepted and durably recorded | none |
  | `400` | `malformed` | Envelope malformed or canonicalization invalid | do not retry |
  | `401` | `sig_invalid` | Signature verification failed | do not retry |
  | `403` | `key_unknown` | No authoritative key for `kid` | refresh, then retry |
  | `403` | `not_permitted` | Sender authenticated but refused by receiver policy | do not retry |
  | `409` | `duplicate` | `msgid` already processed | do not retry |
  | `410` | `key_expired` | Matching keys exist but no epoch covers `ts` | rotate, then retry |
  | `422` | `stale` | `ts` outside the freshness window | do not retry |
  | `421` | `overloaded` | Temporary receiver overload | retry with backoff |
  | `429` | `rate_limited` | Rate limited | retry with backoff |
  | `503` | `unavailable` | Temporary failure | retry with backoff |
  | `505` | `version_unsupported` | `v` unknown to the receiver | do not retry (fail closed) |

## 5.4 Retry and reliability

- **REQ-5.6** Senders MUST retry `421`, `429`, `503`, and network failures with
  exponential backoff and jitter, and MUST resend byte-identical content with
  the same `msgid`. The sender MUST NOT alter `ts`, `msgid`, `payload`, or
  `sig` between retries.
- **REQ-5.7** Delivery is **at-least-once**: the sender retries until `202`,
  and the receiver deduplicates by `msgid`. `202` is the commit point; the
  receiver MUST NOT return `202` before the message and its `msgid` are
  durably recorded. `[SEC-3]`

## 5.5 Receiving policy

- **REQ-5.8** Receivers MUST NOT act as open relays (REQ-1.5) and MAY apply
  allow-lists, block-lists, rate limits, and quotas as local policy. The
  protocol defines no reputation scoring (REQ-1.4).
- **REQ-5.9** A receiver that accepts a message from an unknown sender SHOULD
  record `(domain, kid, ts, sig, message)` for attribution and audit.
- **REQ-5.10** Implementations MUST document whether their default receiving
  policy is open or closed, and how a sender seeks permission to be accepted.
  *(non-normative)* A closed inbox that looks open wastes senders' retries; a
  transparent default lets senders and users act correctly.
- **REQ-5.11** A receiver that authenticates a message but refuses it as a
  matter of policy MUST respond `403` with token `not_permitted`, distinct from
  `key_unknown`. Authenticated senders MUST NOT be silently discarded, so that
  they do not retry indefinitely. A receiver MAY answer all policy refusals
  with a uniform `not_permitted` in order not to disclose its policy.
- **REQ-5.12** A sender MUST treat `202` and `409` alike as **delivered**: a
  duplicate means the receiver has already processed that `msgid`, so the
  sender's obligation is met and it MUST NOT retry or report failure.

# 6. Receiver Verification

## 6.1 The gate

- **REQ-6.1** A receiver MUST evaluate an incoming envelope in the following
  order, stopping at the first failure:

  1. **Version** — the envelope MUST carry an integer `v`. A missing or
     non-integer `v` responds `400` (`malformed`); a well-formed `v` that the
     receiver does not implement responds `505`
     (`version_unsupported`). `[SEC-7]`
  2. **Well-formedness** — structure, member types, sizes, base64, and
     canonical bytes MUST be valid; otherwise `400`. The received body MUST be
     byte-identical to the canonical serialization of its members (REQ-4.7); a
     body that would require re-serialization to become canonical, or that
     repeats a member name, is malformed. A receiver MUST NOT re-serialize a
     body in order to verify it (Annex B, B.7).
  3. **Sender key** — resolve the sender's key for `from` and `kid`
     (REQ-2.10). Respond `403` if unknown, `410` if only expired epochs match.
     A **transient** failure to consult the key records — for example a DNS
     timeout — MUST respond `503` (`unavailable`) and MUST NOT be treated as an
     unknown key: `403` is final, whereas a temporary failure is retried
     (REQ-5.6).
  4. **Signature** — verify `sig` over the canonical bytes (REQ-4.8) under the
     resolved key. Otherwise `401`. `[SEC-1]`
  5. **Freshness** — `ts` MUST satisfy `now − W ≤ ts ≤ now`, where `W` is
     receiver policy with a default of `300` s (a receiver MAY use a smaller
     window); otherwise `422`. `[SEC-6]`
  6. **Replay** — the `msgid` MUST NOT have been accepted before from the same
     sender domain; otherwise `409`. `[SEC-3]`
  7. **Accept** — durably record the message, mark `msgid` processed, respond
     `202`.

- **REQ-6.2** The processed-`msgid` state MUST NOT be modified by any message
  that has not passed step 4. *(non-normative)* Ordering authentication before
  the replay check prevents a forged message from suppressing a genuine one by
  pre-claiming its id; a receiver MAY apply rate limiting before step 4 but
  MUST NOT let such traffic mutate acceptance state.
- **REQ-6.3** A message that fails any step MUST NOT be accepted, MUST NOT be
  marked processed, and MUST NOT be delivered.
- **REQ-6.4** Acceptance MUST be atomic with respect to marking: `202`
  implies both the stored message and the marked `msgid`. `[SEC-3]` The store
  MUST complete **before** the `msgid` is marked: if the store fails, nothing
  is marked and the sender's retry is a fresh attempt (`503`), never a
  spurious `409` — a message that cannot be stored MUST NOT be lost by
  acknowledging it.
- **REQ-6.5** A receiver MUST NOT accept a message whose `to` does not name an
  address it serves; it MUST respond `403` (`not_permitted`). This check is
  performed after step 4 (signature) and before step 5 (freshness): a refusal
  is therefore only given to an authenticated sender, and an unsigned probe
  cannot elicit it.

## 6.2 Security goals

The `SEC-n` tags used throughout this document are defined here. `SEC-1`…
`SEC-5` were inherited from the pre-v0.1 scaffold; `SEC-6` and `SEC-7` are
additions of this revision.

| Goal | Statement | Protecting requirements | Formal status |
|---|---|---|---|
| **SEC-1 — Sender authentication** | A message accepted from `local@domain` verifies under a key that `domain` publishes for `local`, whose epoch covers the message's `ts`. | REQ-1.1, REQ-2.10, REQ-4.8, REQ-6.1.3–4 | **Proved:** `Imp.validate_ok_implies_sig`, `validate_ok_implies_valid_at`, `accept_implies_security` (given REQ-4.10) |
| **SEC-2 — Integrity** | The signature binds exactly one envelope; any alteration of a signed member invalidates it. | REQ-4.7, REQ-4.8, REQ-4.9 | **Proved:** framing (`Imp.body_injective`, `Imp.signatureInput_injective`), decimal and JSON strings (`Imp.encNat_injective`, `Imp.encStr_injective`), base64 in full (`Imp.encB64_injective`, via the alphabet, padding, and `Imp.decB64_encB64`), the `to` framing (`Imp.encArray1_injective`), and fields (`Imp.envelope_eq_of_fields`) |
| **SEC-3 — Replay resistance and idempotency** | A `msgid` is accepted at most once per sender domain; acceptance marks it atomically; retries cannot double-process; acceptance never un-marks. | REQ-4.3, REQ-5.6, REQ-5.7, REQ-6.1.6–7, REQ-6.4 | **Proved:** `Imp.validate_ok_implies_unseen`, `accept_once_marks_id`, `accept_once_blocks_duplicate`, `accept_once_keeps_old`, `processAll_keeps_old` |
| **SEC-4 — Rotation safety** | A key becomes authoritative only via cross-signature by a then-authoritative key; a key id never reappears; a valid chain contains no key introduced without such a signature. | REQ-2.8, REQ-3.2, REQ-3.3, REQ-3.5 | **Proved:** `Imp.validChain_stepwise`, `validChain_head_not_in_tail`, `rotates_ok_keys_distinct` |
| **SEC-5 — Rotation availability** | Rotation requires overlapping epochs, so a message timestamped during a transition verifies under at least one published key. | REQ-3.4 | **Proved:** `Imp.rotates_ok_requires_overlap` |
| **SEC-6 — Freshness** | An accepted message's `ts` lies within the receiver's freshness window and within the resolved key's epoch. | REQ-2.10.3, REQ-4.4, REQ-6.1.5 | **Proved (epoch):** `validate_ok_implies_valid_at`. **Open:** wall-clock window (§9 #2) |
| **SEC-7 — Version integrity (no downgrade)** | The wire version is covered by the signature, so it cannot be altered; an unknown version is rejected fail-closed; a message cannot be relabelled across versions. | REQ-4.7, REQ-4.8, REQ-6.1.1, REQ-7.1, REQ-7.2 | **By construction:** `v` is a signed member (so alteration breaks SEC-2), and the gate rejects unknown versions before any other processing |

## 6.4 Threat model

**Attackers considered.**

1. **Network attacker** — may read, drop, duplicate, reorder, or modify
   traffic. In v0.1 it cannot break TLS.
2. **DNS attacker (no DNSSEC)** — may read, forge, or delete DNS records for
   domains that do not sign their zones, including records of this protocol.
3. **Key-compromise attacker** — has obtained a private signing key.
4. **Malicious sender** — holds a valid identity and misbehaves (spam,
   phishing).

**Assumed sound (trusted, not proved).** Ed25519 signature soundness and
SHA-256 collision resistance; the TLS public-CA trust model; DNS as an
unauthenticated distribution channel; and the binding between a `kid` and its
public key as obtained per REQ-2.10.

**Guaranteed.** The goals `SEC-1`…`SEC-7` of §6.2, each of which is either
machine-checked or explicitly tracked as an open obligation.

**Explicitly not guaranteed.**

- **Confidentiality beyond transport.** v0.1 has no end-to-end encryption
  (REQ-1.7). The delivery endpoint and any host in front of it see plaintext
  payloads.
- **Availability against DNS deletion.** An attacker able to delete records
  can cause fail-closed rejection — a denial of service. Authenticity is not
  broken: `SEC-4` prevents *introducing* a key without a cross-signature.
- **First-contact authenticity without DNSSEC.** For a domain a receiver has
  never held before, a DNS attacker can plant records. REQ-3.1 delegates
  first-contact policy to the receiver; DNSSEC removes this exposure. Email's
  SPF/DKIM and DANE share the same shape.
- **Sender behaviour.** The protocol authenticates but does not judge. Spam or
  phishing from a valid identity is receiver policy (§1.7).
- **Compromised or delegated keys.** A stolen key is impersonatable until
  revoked (REQ-3.6), bounded by the cache lifetime (REQ-2.11). A namespace
  owner can substitute keys for delegated labels (REQ-2.9).
- **Endpoint and storage security.** Compromise of the receiver's host,
  storage, or policy engine is outside the protocol's scope.

**Residual risks accepted.** First-contact DNS forgery (mitigations: receiver
policy per REQ-3.1, DNSSEC); DNS-deletion denial of service (redundant
publication); key theft (rotation, revocation, TTL bounds); spam to an open
inbox (receiving policy, §1.7). Each risk is accepted *explicitly*, not
overlooked.

# 7. Compatibility and Versioning

- **REQ-7.1** The wire version `v` MUST be a member of the signed envelope
  (REQ-4.8), so a version cannot be altered without invalidating the
  signature. `[SEC-7]`
- **REQ-7.2** A receiver MUST reject an envelope with an unknown `v`
  (`505`) — fail closed, never guess.
- **REQ-7.3** The protocol freezes its **rules**, not its **bytes**:
  receivers MUST tolerate members they do not recognize; canonical
  serialization covers the complete member set (REQ-4.7); and no extension may
  add a member that is *required* to process a message without a version bump.
  Unknown members MUST NOT alter the verification semantics of defined
  members.
- **REQ-7.4** New message types and future features are added through the
  additive **registry** specified in [`registry.md`](registry.md). Its naming
  rules and registration procedure (`REQ-R.*`) are normative; registered
  additions MUST NOT change the verification semantics of core messages.
  Unregistered names remain permitted but carry no standardized meaning.
- **REQ-7.5** v0.1 defines no capability negotiation. A lightweight
  capability exchange is deferred until a feature requires it (for example
  replies or E2EE).
- **REQ-7.6** v0.1 implementations MUST remain interoperable for the life of
  the protocol. A breaking change requires a new wire version with a defined
  coexistence and deprecation path. Silent behavior changes are prohibited.
- **REQ-7.7** Document and software versions use semantic versioning; the wire
  version is independent of both.
- **REQ-7.8** Any normative change to verification semantics MUST be
  accompanied by updated Lean proofs. `[U5]`

# 8. Conformance

- **REQ-8.1** This specification's normative **test vectors** are Annex B
  (`conformance.md`) with machine-readable data in `vectors/v0.1.json`: test
  identities, key records, envelopes, canonical byte strings, rotation cases,
  and expected outcomes. Where the two disagree, the JSON governs.
- **REQ-8.2** The vectors MUST include negative cases: invalid signature,
  unknown `v`, replayed `msgid`, expired epoch, unknown `kid`, malformed
  canonicalization, stale `ts`, and an unknown future member that must be
  tolerated.
- **REQ-8.3** The specification is complete only when at least three
  independent implementations interoperate against it — meaning an implementer
  can build a conforming sender and receiver from this document alone, without
  consulting the authors.
- **REQ-8.4** There is no official implementation. Conformance is judged by
  the test vectors, not by similarity to any codebase.

# 9. Formalization Status and Open Obligations

**Proved (Lean 4, `Imp` namespace).** The validation gate's implications,
replay resistance and state preservation, key chain rotation safety and
availability, field-level envelope injectivity, the canonical byte **framing**
(`Imp.Canonical`), and the **decimal** and **JSON-string** encoders
(`Imp.Text`) — as mapped in §6.3. All modules build with `lake build +Imp`.
No proof uses `sorry` or `Classical.choice`; the proofs rely only on Lean's
standard logical axioms — `propext` throughout, plus `Quot.sound` (Lean's
quotient axiom) in `Imp.Text` and `Imp.Base64`.

**Open obligations (tracked; none affect the meaning of the proofs above):**

1. ~~**Canonical framing** (REQ-4.9)~~ — **closed**: `Imp.encBlocks_injective`,
   `Imp.body_injective`, and `Imp.signatureInput_injective` prove the
   self-delimiting block framing determines the members.
2. **Freshness window** (REQ-6.1.5): model `now − W ≤ ts ≤ now` and prove the
   gate's freshness implication.
3. **Concrete cryptography** (REQ-4.10): instantiate the abstract signature
   scheme with Ed25519/SHA-256 (assumed sound in v0.1).
4. **DNS fetch and cache model** (REQ-2.11): bounded cache lifetime and
   fail-closed expiry; revocation semantics (REQ-3.6).
5. ~~**Cross-signature bytes** (REQ-3.2)~~ — **closed**: the signed byte form
   is now pinned in REQ-3.2 and exercised by rotation vectors R1–R5.
6. ~~**Test vectors** (REQ-8.1)~~ — **closed**: Annex B (`conformance.md`) and
   `vectors/v0.1.json`, self-checked so every signature verifies or fails as
   stated.
7. **Delegation runtime** (REQ-2.9): specified here; implementation and any
   additional formal treatment are future work.
8. ~~**Member textual encoders** (REQ-4.9)~~ — **closed**: minimal decimal
   (`Imp.encNat_injective`) and JSON string escaping (`Imp.encStr_injective`)
   in `Imp.Text`; base64 in full in `Imp.Base64` (bit packing, alphabet,
   padding, `Imp.decB64_encB64`, `Imp.encB64_injective`); the v0.1 `to`
   framing (`Imp.encArray1_injective`). A future **multi-recipient** array
   framing would need a separator-aware encoder and is not part of v0.1.
9. ~~**Registry procedure** (REQ-7.4)~~ — **closed**:
   [`registry.md`](registry.md) specifies the extension points, naming rules
   (unqualified names reserved; reverse-DNS names permissionless), the
   registration procedure, and the initial entries. Its *procedure* is frozen
   with v1; its *contents* grow additively.

**Trusted assumptions.** Ed25519 and SHA-256 soundness; TLS-PKI; DNS as an
unauthenticated transport (REQ-2.12).

# Annex A — Glossary

- **Address** — `local@domain`; the human-usable name of an identity.
- **Canonical serialization** — the single deterministic byte form a message
  is signed over.
- **Epoch** — the `nb`…`na` interval during which a key is authoritative.
- **Fail closed** — when something is unknown or invalid, refuse rather than
  guess.
- **Genesis key** — the first key of an address, bootstrapped out of band.
- **Kid** — key id; base64 of the first 16 bytes of SHA-256 of the public key.
- **Namespace owner** — whoever can publish key records for a domain.
- **Replay** — re-sending a previously accepted message to cause a duplicate
  effect; prevented by `msgid` tracking.
- **Rotation** — replacing the current key with a successor, cross-signed by
  the current key, with overlapping epochs.
- **At-least-once** — the delivery guarantee: retries until acknowledged;
  duplicates are possible and are removed by `msgid` deduplication.
